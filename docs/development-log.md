# Development Log — Smart Hostel Management System

This log records **real** problems hit during development, in the order they happened.
It is the only source used for the "Problems Encountered and Solutions" sections of the reports.

---

## 1. Seed script stopped on a duplicate registration number

- **Date:** 2026-10-07
- **Phase:** 6 (seed dataset)
- **Problem:** Loading `08_seed_data.sql` stopped at the 122nd student.
- **Error message:**
  ```
  ORA-00001: unique constraint (USER1.UQ_STUDENT_REGNO) violated on table USER1.STUDENT columns (REGISTRATION_NO)
  ORA-03301: (ORA-00001 details) row with column values (REGISTRATION_NO:'24BYB1001') already exists
  ```
- **Cause:** The seed generator gives the first student a fixed, documented registration number
  (`24BYB1001`, the demo student account). The random generator later produced the same number for
  another 3rd-year Cyber Security student. The `UNIQUE` constraint on `REGISTRATION_NO` correctly rejected it.
- **What was tried / fixed:** The generator now keeps a set of used registration numbers, with the demo
  number reserved from the start, and keeps drawing until it gets an unused one.
- **Files affected:** `database/seed/generate_seed.py`

## 2. SQL*Plus committed half of a failed script

- **Date:** 2026-10-07
- **Phase:** 6
- **Problem:** After the failure above, the database already contained 6 hostels and 121 students,
  although the script had stopped with an error.
- **Cause:** `run-sql.sh` used `WHENEVER SQLERROR EXIT SQL.SQLCODE`. In SQL*Plus, `EXIT` **commits by default**,
  so every row inserted before the error was kept.
- **Fix:** Changed the directive to `WHENEVER SQLERROR EXIT SQL.SQLCODE ROLLBACK`, so a failing script leaves
  no partial data. Added `drop-all.sql` + `reset-db.sh` to rebuild the schema cleanly.
- **Files affected:** `database/run-sql.sh`, `database/drop-all.sql`, `database/reset-db.sh`, `database/run-all.sh`

## 3. Procedures, functions and triggers became INVALID after seeding

- **Date:** 2026-10-07
- **Phase:** 6
- **Problem:** After `run-all.sh`, the verification query showed only 2/4 functions, 0/6 procedures
  and 1/4 triggers as `VALID`.
- **Cause:** Seed rows are inserted with explicit IDs, so the end of the seed file runs
  `ALTER TABLE ... MODIFY (... GENERATED BY DEFAULT AS IDENTITY (START WITH LIMIT VALUE))` to move each
  identity sequence past those IDs. `ALTER TABLE` is DDL, and Oracle marks every PL/SQL object that depends on
  an altered table as `INVALID`. (Oracle would recompile them on first use, but they should not be left invalid.)
- **Fix:** The seed file now ends with `EXEC DBMS_UTILITY.COMPILE_SCHEMA(schema => USER, compile_all => FALSE);`.
  After rebuilding: 4/4 functions, 6/6 procedures, 4/4 triggers `VALID`.
- **Files affected:** `database/seed/generate_seed.py` (generates `08_seed_data.sql`)

## 4. Synthetic data was unrealistic in ways the queries exposed

- **Date:** 2026-10-07
- **Phase:** 11 (SQL queries)
- **Problems found while checking query output:**
  1. **Q5** (categories with average resolution time > 2 days, `HAVING`) returned *all six* categories with
     averages between 2.2 and 2.9 days, because every complaint got the same random 3–120 hour resolution time.
  2. **Q6** (overdue complaints) listed the demo student's complaint as `Open` for 74 days, because the demo
     student's statuses were forced without adjusting the complaint dates.
  3. **Q6** also showed a complaint "handled by" *Suresh Iyer*, the name of the demo **warden**. The demo staff
     names were hard-coded but not added to the generator's used-name set, so a random maintenance worker
     received the same name.
- **Fixes:**
  1. Resolution time now depends on the category (housekeeping 2–30 h … carpentry 24–168 h) and is halved for
     High priority. Q5 now returns only Carpentry (3.3 days) and Other (2.1 days).
  2. The demo student's complaints are dated 40, 25, 6, 3, 1 and 0 days ago, matching their statuses.
  3. All hard-coded demo names are reserved in the used-name set. Verified with a query: no duplicate names across
     STAFF and STUDENT, and 0 complaints assigned to non-maintenance staff.
  4. Complaints older than 30 days are always Resolved.
- **Files affected:** `database/seed/generate_seed.py`

## 5. Two demo checks tested the wrong rule

- **Date:** 2026-10-07
- **Phase:** 12 (PL/SQL testing)
- **Problem:** In `10_demo_transactions.sql`:
  - the "maintenance staff tries to allocate a room" check returned `ORA-20011 Student already has an active
    room allocation` instead of the staff-role error, because it reused the student who had just been allocated;
    `sp_allocate_room` checks the student before the staff member.
  - the "delete a hostel that still has rooms" check was blocked by `FK_MENU_HOSTEL` (an extension table)
    instead of a core foreign key, because Oracle reports whichever child table it finds first.
- **Fix:** The role check now uses a different waiting student (result: `ORA-20014 Only an Admin or Warden can
  allocate rooms`). The FK check now deletes a room that has allocations (result: `ORA-02292 ... FK_ALLOC_ROOM`).
- **Files affected:** `database/transactions/10_demo_transactions.sql`
